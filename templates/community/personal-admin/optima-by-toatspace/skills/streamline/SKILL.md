# streamline

Use /streamline when method mixes with live status. Separate them so durable law does not drift and live truth does not go stale inside method docs.

## LOCKED
Durable method or quality law. Must not change because today’s ticket moved. Lives in skill bodies, ALWAYS-style law files, permanent checklists, public method pages. Examples: gate criteria, ownership, always-on audit rules, stable vocabulary, restore/bootstrap steps.

## FLOWING
Live actionable state. Edit when work moves; lag allowed until refresh. Keep in a live status file that method docs only point to. Examples: open items, counters, session ids, who is mid-task, last-checked timestamps.

## Separation
| Kind | Where | When it changes |
| LOCKED | Method / skill / quality law | Only when owner revises method |
| FLOWING | Live status file | Whenever work moves |

Method may say “For live state, read <status pointer>” — never embed today’s numbers/ids/next-steps as law.

## Evidence
LOCKED: cite method/skill path, LOCKED/ALWAYS tag, or public method text. FLOWING: cite status file, live-truth pointer, or expected-to-change evidence. Missing source = unknown.

## Short test
If work advanced tomorrow and nobody revised the method, would this sentence still be true? Yes → LOCKED. No → FLOWING.

## Anti-patterns

1. **Ephemeral as law** — Baking open items, session ids, percentages, or "next page" into a skill/`ALWAYS` file. That freezes yesterday's progress as tomorrow's method.
2. **Method goes stale** — Writing live progress into method docs, then refusing to edit the method because "law shouldn't change," so both sides rot.
3. **Dual homes** — Same fact edited in method and status without a single live pointer. Pick one FLOWING home; method only links.
4. **Silent promotion** — Copying a FLOWING line into LOCKED text "for convenience" without an owner method revision.
