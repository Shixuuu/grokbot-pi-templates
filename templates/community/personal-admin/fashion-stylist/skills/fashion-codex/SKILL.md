# Fashion Codex

A branded PDF book of the user's personal style, built from their real closet. It is the finished product that the catalog, closet, and profile skills feed into.

## Explain it first

Users don't know what a Fashion Codex is. The first time it comes up, say it plainly: "your Fashion Codex is a personal style book of your closet: every piece you own on catalog pages, outfit combinations, your favorite looks, and a snapshot of your style." Once the user has about 8 or more pieces filed, offer once to build one sample page (a category page) so they can see what they're building toward.

## How it gets made

1. User snaps phone photos of their clothes (hanger or flat on a bed is fine).
2. Clean product shots via [Fashion asset from photo](sand-workflow:fashion-asset-from-photo): approve a short prompt first; remove background, hangers, tags, clutter; product lighting. The user can add polish prompts such as "remove wrinkles" or "make the item symmetrical".
3. File each piece into the virtual closet ([Virtual closet](sand-workflow:virtual-closet), [Fashion catalog pages](sand-workflow:fashion-catalog-pages)) with name, brand, color, and SKU.
4. Build outfits, try-ons, and videos as wanted.
5. Assemble the Codex PDF (see Build method).

## Closet records

- **SKUs:** one letter per category plus three digits: D dresses, T tops, S skirts, P pants and shorts, J jackets, H shoes, A accessories, JW jewelry, NS layered necklace looks, BS bracelet stacks (the same letters as the catalog and closet skills; add letters as needed and record each in its registry). Keep one registry file per category listing every SKU and the next free number. Never reuse a SKU.
- **Names:** short and descriptive. Knee-length pieces are "Midi," not "Mini." Never put the user's size in names or captions.
- **What goes in:** only pieces the user owns and keeps. Sleepwear stays out. Ask the user to tag each piece warm, cool, or all-season when it's filed. Season-only pieces stay out of the wrong season's mixes.
- **Color families:** give each color family a name (playful names are fine if the everyday color stays obvious, e.g. "Sea Glass — solid aqua"), plus a skip list of colors the user avoids. Group the closet's raw colors into 6–10 families when building the Style File (ask whether the user wants playful names or plain ones), and use the same names on the Style File, captions, and snapshot charts.

## Book order

1. **Cover** — "{Name}'s Fashion Codex", italic subtitle "Personal Style Catalog", a hero image (a try-on or favorite look), optional signature and © line. White page, one accent color, no border, no crop marks, **no page number**.
2. **Contents** — page 2; numbering starts here.
3. **Style File** — the one-page profile visual from [Fashion profile](sand-workflow:fashion-profile).
4. **Category pages** — header "{Name}'s Closet" with the category as subtitle (Dresses, Formal, Tops, Long Sleeves, Skirts, Pants, Swim & Cover-Ups, Outerwear, Shoes, Accessories, Purses, …). Shoes get their own page, split into sections by type (Sandals, Heels, Boots, …); every shoe goes in exactly one section. Accessories has sections for Hats and Scarves (a section with nothing yet shows a gray "None yet."). Purses get their own page once there are about 3 or more; otherwise they sit on Accessories. Jewelry comes after Purses (see Jewelry section). Pages follow the order of this list. A category with fewer than 3 pieces shares a page with the categories next to it in this list (e.g. "Pants & Shorts"), each keeping its own left-aligned sub-header, instead of standing alone.
5. **Jewelry pages** (when the user has jewelry): Jewelry catalog, Layered Jewelry Looks, Favorite Jewelry Look (hero), Favorite Jewelry Looks, Necklace Layering. See Jewelry section.
6. **Mix Fashion File** — title page naming their favorite look, hero flat-lay of that outfit.
7. **Favorite Pairings** — the user's hearted looks as outfit tiles. This opens the Mix section and is the book's only favorite-outfits page.
8. **Collection Snapshot** infographic.
9. **Mix-and-match outfits** — every kept top + bottom look, sorted by color and numbered.
10. Optional: a Favorites page collecting every hearted piece.

**Custom sections:** status lanes (Incoming, Returns, Order Complete, Shopping Favorites) and order tracking are not standard. Add one only if the user asks for it as a custom section, kept in its own file.

## Page rules

- Every page is the same size: A4 portrait, 1240×1754 px (150 DPI). White background, lots of whitespace, centered light titles, left-aligned sub-section headers, page numbers as centered bottom footers only.
- **Grid layout (like a product catalog):** a **4×4 grid, 16 pieces per page**: 4 across, 4 rows down, filled left to right then top to bottom. When 16 are placed, start the next page. Every cell is the same size, with even gaps and rows lined up on the page and from page to page. Pieces float on the white page with **no tile boxes or borders**, each centered in its cell and scaled to the same height so the rows look even, with its caption directly underneath. A short last row stays left-aligned, and a lone item never gets blown up. Outfit pages use the same grid, with each look's pieces stacked in one cell column (top above bottom).
- **Never crop the original photo.** Show the whole asset, scaled down with white margins if needed, inside its cell.
- **Order on a category page:** favorites first within each section, then everything else in rainbow color order (pinks and reds, corals and oranges, yellows, greens, blues and aquas, purples, then neutrals: white, cream, beige, brown, gray, black; within a family, light to dark, so aqua before navy; a print sorts by its main color); clean product shots before on-body photos. When a page fills, start a new page for the next color.
- **Catalog captions** (centered, 2 lines, small): Name, then Brand · Color · SKU. Favorite names are tinted in the accent color.
- **Look, Favorites, and One-Look captions** (under each garment tile): Name / SKU / number of looks it's in.
- **Favorites:** exactly one small pink heart per favorite, at the top-right corner of its cell. No hearts in captions or next to counts. Every page uses the same heart image so they match.
- **Type:** lock one set of sizes (title, section header, item name, meta line, footer) and check every page against it; the Style File may use a larger title. Suggested fonts: a clean sans for headers (e.g. Raleway), a serif for body (e.g. Crimson Pro).
- Accent color: soft pink by default, or the first favorite color on the Style File.
- Charts use the book's own fonts and accent color, not a chart library's defaults.
- Footers carry the page number only. Anything else (like an "example data" label) goes on the cover.

## Jewelry

Build this once the user has a few pieces of jewelry filed. Same page style, grid, captions, and hearts as the clothing pages.

1. **Jewelry** catalog page: sections Necklaces, Earrings, Bracelets (favorites first in each). Captions: name, then materials · SKU (JW###). Earrings can stay grouped studs, dangles, hoops, statement inside the favorites-first order.
2. **Layered Jewelry Looks**: sections "Layered Necklaces" (NS###) and "Layered Bracelets" (BS###). Each look is built from real isolates of the user's own pieces and captioned with its name and the pieces in it (e.g. "JW010 + JW009 · NS001"). The user hearts favorites.
3. **Favorite Jewelry Look** (hero): in the Mix Fashion File title-page style. The user's #1 jewelry look large on top (e.g. a layered necklace), matching earrings and bracelet below, with brand and SKUs underneath.
4. **Favorite Jewelry Looks**: the hearted jewelry looks as rows of the same thumbnails, each labeled with its pieces.
5. **Necklace Layering**: suggested necklace stacks generated from a rule, like the Mix pages (the logic proposes, the user hearts). Rule: stacks of 2 or 3, ordered top to bottom by length, each next necklace at least 1 inch longer; a collar only on top; pendants or beaded strands below. Record each necklace's type (collar, pendant, or strand) and length. Combine pieces only by scaling and placing them; never recolor or reshape them.

**Jewelry try-ons:** jewelry try-ons are not built into Fashion Stylist yet. If the user wants one anyway, you can attempt it.

## Mix curation

1. Pair every top with every bottom (skirts, shorts, pants).
2. Propose keep or drop for each pair with a one-line reason (clashing prints, muddy colors, duplicate of a stronger look, wrong season), then let the user approve or change the list. Record kept/dropped counts.
3. Ask the user to heart their favorite looks. Matching sets are always favorites. The hero/cover look is the one the user names; if they don't, suggest the favorite look whose pieces are both hearted and in their favorite colors (if several qualify, offer them and let the user pick), and label it "suggested" until they confirm. The user has the final say; swap any piece in one sentence.
4. Versatility = number of kept looks a piece appears in. Break ties by favorites (more hearted looks wins); if still tied, show the tied pieces by name, not just "tie."
5. Season: a look is cool-weather if it has a cool-only piece, warm-weather if it has a warm-only piece, and all-season looks count toward both. Untagged pieces count as all-season.

**When the user isn't around to answer** (color family names, keep or drop, favorites, season tags): use plain defaults, label them "proposed" on the page, and confirm with the user before treating them as final.

## Collection Snapshot

- Count boxes: total looks and looks by bottom type; warm-weather, cool-weather, and favorite looks.
- "#1" row: most versatile piece, top, bottom; favorite mix look.
- Pie chart of separates by type; bar chart of most common outfit colors.
- Deeper Mix Data pages (optional, a few pages): color palette, versatility rankings, top picks by category, favorites, one-look wonders (pieces in only one look), what they have plenty of, what's missing.
- Let the user drop a category from climate counts when it skews them (e.g. athletic wear).
- Stat boxes run margin to margin; each row matches the width of the row above. Large type (it's usually viewed in chat or as a preview). Make sure the bottom source line isn't clipped by the footer.
- **Use only real counts from the closet and outfit list. Never invent numbers.**

## Build method

1. Render each page as its own 1240×1754 image (e.g. Python + Pillow), one builder script per page type, reading from the closet registries and asset files.
2. Merge the page images in book order into one PDF, burning continuous page numbers (skip the cover). Regenerate the Contents page from the final order every time.
3. When pasting in a page from another PDF, blank out its own footer or credit line so nothing appears twice.

## Locks

When the user says "lock it," save a written reference of that page (what's on it, sizes, order) and freeze it. Change a locked page only when the user unlocks it.

## Rebuild checklist (common mistakes)

- If a builder regenerates a page from a stored source or backup image, **fix the source, not just the output**, or the next rebuild brings the old version back. Rename old sources (e.g. suffix OLD) instead of deleting.
- After renaming a section, update the Contents page and every page title to match.
- After every rebuild: check the page count, confirm locked pages are unchanged, and render and look at every changed page before sending.
- Rebuild affected pages (and the snapshot) whenever the closet or favorites change.
- Adding a page (like Shoes or a Jewelry page) shifts later page numbers: regenerate Contents and check every page after it.

## Delivery

One page asked for: render it and send it as an image. Whole book asked for: attach the full PDF.

## Day-to-day rules

- Plan accessories first; reuse pieces across outfits so they pack less.
- Packing: work from the closet, the Style File, and trip details the user gives (location, weather, itinerary, occasions). Give a packing list, and offer packing options as photo grids of their own clothes with must-haves locked in. Locked pieces stay put when other pieces are swapped.

## Public-template rules

Works for any user's own photos and taste. No private IDs, contacts, payments, or private site lists. Image and video steps depend on the user's own image-generation access.
