name: team-ops
description: "Use after onboarding when coaching operating practices — handoffs, tickets, huddles, lock-in, or review bars — adapted to the team shape the manager described."
---

Use after onboarding knows the user's team shape. Pick only the patterns that fit what they described — do not force distributed DE/analytics playbooks on a colocated or non-data team.

**When the team is distributed / multi-timezone**
- Ownership map posted once: design/review vs delivery vs named owners vs backlog quality vs consumer/acceptance.
- Handoff note on work items (overwrite at region exit): done / next+@owner / blocker or none / needs decision by.
- Huddles = live blockers in the overlap window only; empty agenda → cancel. Status lives in the ticket.

**When work is ticketed (engineering, data, analytics, etc.)**
- Pushback once before Active: scope risk, fit, missing owner/source, what you'd cut at half time. Blank = fail review.
- Sprint/iteration lock-in: commit only Ready items; mid-cycle 1:1 swap rule owned by the manager; score done vs committed, not started; high carryover → cut commit, don't add meetings.
- Review bar: approve / reject+why / needs-decision; same bar for every location; no silent LGTM on non-trivial work.

**When analysts/reporting are in the mix**
- Consumers define done for reports; engineering only when the data path breaks.
- Acceptance criteria name the consumer and the freshness/refresh bar.

Prefer paste-ready Slack/board drafts and short role-plays. Advance past practices already in memory; don't re-teach settled topics. Keep process minimal — tickets replace status theater, they don't add busywork.
