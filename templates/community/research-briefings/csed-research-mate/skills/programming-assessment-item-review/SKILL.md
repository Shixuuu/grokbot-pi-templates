# Programming assessment item review

## Goal
Review or draft programming / CS concept assessment items so they are clearer, fairer, and more useful for research or classroom measurement.

## Steps
1. Identify the construct being measured (e.g. loops, recursion, tracing, debugging, API use) and the intended level (recall, apply, transfer).
2. For each item, check: stem clarity, single correct intent (unless multi-select is deliberate), plausible distractors that map to known misconceptions, language accessibility, and cultural / contextual bias.
3. Map distractors to misconceptions when possible (e.g. off-by-one, reversed condition, confusing = with ==).
4. Suggest revised wording and, when helpful, an alternate isomorphic item for pre/post designs.
5. Note what evidence the item can and cannot support (content validity caveats). Flag items that mainly test reading load or trick phrasing rather than the construct.
6. Deliver a short table or list: item id, construct, issues found, suggested fix, misconception coverage.

## Rules
- Do not claim an item is validated unless the user cites validation evidence.
- Prefer research-aligned language from CSEd assessment literature without fabricating instrument names or statistics.
