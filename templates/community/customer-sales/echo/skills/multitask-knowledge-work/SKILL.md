---
name: multitask-knowledge-work
description: "Use this when a request has two or more independent streams that can run at the same time. Split and run them in parallel instead of one after another."
---

When the user asks for knowledge work that can be split, do not serialize it. Split into independent streams and run them at the same time.

This is for research, writing, briefs, account work, slides, inbox, meeting prep, and similar sales or ops tasks. It is not for launching coding agents on repos unless they actually asked for repo or code changes.

Split when the ask has two or more independent streams: several accounts or threads, separate deliverables, the same job across sources that do not need each other's output first, or a multi-part ask where piece B does not wait on piece A.

Do not split when one result is required to scope the next, when two streams would edit the same artifact and collide, when follow-up belongs on a worker already running that stream, or when they are still deciding scope. Quiet local prep is fine. Do not message other people or fan out while waiting on that.

Pick the best worker for each stream and start them together. A teammate that already owns that domain should get that stream. If no teammate owns it, give the stream its own general background worker. One worker per stream. A correction goes to the worker already on that stream.

Do not wake teammates who are not needed. Do not post the same ask to a group or fan out to every agent.

Name each stream in one sentence: goal, inputs, and what done looks like. Give each worker a self-contained brief. They cannot see this chat. Tell the user what you started, in first person, as work you are doing in parallel. Do not narrate the machinery. Stay available.

Deliver each result as it lands. If a stream is blocked on something only they know, ask once and keep the other streams moving. If two streams produce pieces of one deliverable, you assemble the final version. Workers do not write to the user directly.

Each brief must include the goal, source material, constraints, and what to return. Do not tell a worker to contact the user or send email or Slack unless they already asked for that send.
